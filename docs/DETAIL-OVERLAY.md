# 详情浮层（备案）

**状态：E 与 A 都已做。** A 的形态与三条取舍见下面「已做：方案 A」。这份文档记的是
已经谈定的判断与代价，不是待办清单。

## 问题

详情那一轨原来是写死的 `30rem`（480px）。它**只在窗口窄到一定程度才成为问题**：

| 窗口宽 | 清单那一轨拿到 | 体感 |
|---|---|---|
| 1920 | 1920 − 168(过滤面板) − 480 = **1272** | 不疼 |
| 1280 | 632 | 勉强 |
| 1024 | **376** | 疼：表格开始收列 + 出横向滚动条 |
| 800 | **152** | 很疼：只剩「状态/操作」两列 |

真正要修的是 **< ~1067px** 那一段。

## 已做：方案 E —— 有上限的比例

```css
/* apps/web/src/index.css */
.list-scroll { --w-detail: min(30rem, 45%); }
.list-scroll-has-detail { grid-template-columns: minmax(0, 1fr) var(--w-detail); }
```

- 45% 要到 1067px 才够 480px → **宽窗口行为与从前完全一样**
- 1024 → 详情 460 / 清单 460；800 → 详情 360 / 清单 388
- 一行 CSS，无浮层、无遮罩、不可能抖动，**随时可撤**（把 `--w-detail` 改回 `30rem`）

**它是止损而不是终局**：极窄窗口下详情自己会被压到 300px 以下，README 会挤。

## 已做：方案 A —— 窄到阈值以下时，详情浮在清单上

### 落地的两处与备案不同（实现时才知道的）

1. **判据容器是 `.pane-list`，不是 `.list-scroll`**：容器查询只能给「容器**里面**」
   的元素写规则，而要改网格列的那个元素正是 `.list-scroll`、要浮起来的那个是它的
   子元素 `.detail-pane`——所以容器必须是更外面一层的 `.pane-list`。它的宽度就是
   清单区那一轨的宽度，与 `.list-scroll` 相同（过滤面板收起时一起变宽），判据等价。
2. **详情那一轨有了名字**：`<aside class="detail-pane">`（挂在 `ProjectsPage` 上，
   不挂在 `Outlet` 渲染出来的根节点上——那是页面自己的东西，形状归布局管）。

### 判据

用**容器查询**，问的是 `.list-scroll` 自己的宽度，**不是窗口宽**——过滤面板收起时清单会
变宽，只有容器查询跟得上（仓库里已经是这套，见 `.list-pane` 上的 `container-type`）。

阈值建议 **46rem（736px）**，算术：清单那一轨需要 ≥ 24rem（`仓库 + 状态 + 操作` 收列后的
下限约 14rem，加两侧内边距与一点余量），详情要给到 ≥ 20rem，24 + 20 = 44rem，取 46rem 留余量。
**这个数写在 CSS 一处**，将来觉得早/晚，改它一个。

### 形态

```css
@container (width < 46rem) {
  .list-scroll-has-detail { grid-template-columns: minmax(0, 1fr); }   /* 详情退出栅格 */
  .detail-pane {
    position: absolute; inset-block: 0; right: 0;
    width: min(30rem, 100%);
    overflow: auto;                    /* 它自己滚，不给页面再加一根滚动条 */
    background: var(--color-panel);    /* 不透明：否则下面那一行会透出来 */
    border-left: 1px solid var(--color-line);
    z-index: 4;
  }
}
```

前提是详情那一轨有一个明确的容器元素（`.detail-pane`）。挂在它上面，不要挂 `Outlet`
渲染出来的根节点——那是页面自己的东西，形状归布局管。

### 为什么是这几条

- **绝对定位不参与布局**：浮层出现/消失时，清单的宽度**一个像素都不变**。所以"抖动"
  在这条路上结构性地不可能发生（这是最要紧的一条）。
- **没有遮罩**：点浮层外面就是点清单本身（切项目、点别的行），不触发任何"关闭"。
  抽屉那套「第一次点击被遮罩吃掉」在这里不存在。
- **不做动画**：`grid-template-columns` 的宽度过渡在几个浏览器上会抖；瞬时切换最稳，
  也符合这个软件的气质。要淡入就只淡 `opacity`，别动宽度。
- **关闭只有两条路**，都是已有的：抬头那枚「关闭」、再点当前那一行（反选）。
  不加"点击外部关闭"，不加 Esc（用户把全局快捷键那一层整个删过）。
- **不是模态**：不加 `role="dialog"`、不做焦点圈定——它是一块常驻的面板，不是浮窗。
  清单在后头仍然可达，这正是它和抽屉的区别。

### 代价（明说）

窄窗口下它盖住清单右侧（差异 / 上次检查那两列），而那时清单本来就在横向滚动。
换句话说：**用"遮住一部分"换"清单永远有全部宽度"**。

### 排期：已完成

**当初等壳，是因为壳决定这件事的前提**：窗口能不能被拖到很小的宽度、浮层在 webview 里的
表现（滚动条归谁、要不要配合窗口尺寸做持久化）。那件事已经做完了——壳能起、能跑 release、
数据目录与窗口尺寸都定死了，见 [`src-tauri/README.md`](../src-tauri/README.md) 与
[`SIDECAR.md`](../src-tauri/SIDECAR.md)。**所以这里没有前置条件了**，什么时候做由需求决定。

要做的时机不变：**800px 以下还是难受**——那时再看上面「形态」与「代价」两节。

## 明确不做

- **拖拽调宽**：功能不大，但要把宽度持久化、还要和容器查询打架，收益不抵复杂度。
- **底部抽屉**：用户明确不喜欢「抽屉 + 遮罩」那种感觉（遮罩吃掉第一次点击、看着另类）。
- **方案 B（窄窗口下详情占满清单区，像手机上钻进去）**：详情能拿到全宽、读 README 最舒服，
  但**失去清单上下文**——不能直接点下一个项目，而且和"反选"那套交互冲突。等于换一种信息
  架构，不只是布局。除非以后发现经常在小窗口里读 README，否则不做。

## 做完之后要人眼验的（jsdom 抓不到布局）

`pnpm typecheck` 与全量测试对**位置与宽度一无所知**（jsdom 没有布局引擎）。所以这些只能看：

1. ≥1067px：详情仍是 480px，与改动前一模一样；
2. 1024 / 800px：详情按比例变窄，清单明显变宽，**表格不再只剩两列**；
3. 收起过滤面板时，清单那一轨变宽、详情跟着重算（容器查询的判据是它自己）；
4. 若已做 A：在阈值以下打开项目，**清单不应发生任何位移**（这是 A 的验收点）。

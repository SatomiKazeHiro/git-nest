## 今天的实测规模

只读打开 `data/git-nest.db` 量到的（2026-10-12）：

| | |
|---|---|
| 项目数 | **15**（自己写的 1） |
| 检查记录 | 1246 条（约 83 条/项目，上限 2000/项目，裁剪正常） |
| 数据库 | 268 KB |
| 分类 / 标签 | 4 / 0 |

**所以现在不做。** 连 `docs/DESIGN.md` 自己写的「30–200 行先用普通列表」都还没到——
这个量级上分页只会把数据藏起来、多几次点击，等于给一个不存在的问题加 chrome。

## 真到那天，瓶颈不在表格

表格是每行十来个格子，React 渲染几百行完全撑得住。真正会慢的是**逐仓库跑一次 git 读状态**
（并发限 4）：500 个仓库就是 500 次 git，那才是分钟级的等待。

所以这件事的本质不是"列表怎么画"，而是"**要读多少仓库的状态**"。

## 三条路（到那天先量，再选）

| | 做法 | 收益 | 代价 |
|---|---|---|---|
| (a) | **分页**（放列表下面，用户指定的位置） | 顺带把状态读取量切成 1/N——这是分页最大的实际收益 | 要改接口（limit/offset）、多一层翻页 |
| (b) | **虚拟化**（只渲染可见行） | 渲染开销与行数脱钩 | 状态**照样读全部**，瓶颈没动 |
| (c) | **只给可见行读状态**（IntersectionObserver） | 直接打瓶颈，且不动接口、不影响"一屏能看见多少" | 滚过去才出现状态，有一瞬间的空档 |

**我倾向先试 (c)**：瓶颈确认是 git 读取的话，它是唯一对症的那条；(a) 是它的补充
（数据量再大时连查询与传输也要切）。

## 触发条件（不是"感觉慢"，是可量的）

满足任一条就该做这一轮：

- 项目数 **≥ 100**；
- 清单首屏 **> 2 秒**；
- 「读状态…」在屏幕上停留 **> 10 秒**。

到那天先按上面"今天的实测规模"那一节的方式**再量一次**（项目数 / 检查记录数 / DB 大小），
再用 `pnpm bench:status` 掐一次状态读取的耗时——先有数，再选路。

## 高危

### H1. 前端缓存失效写错 key，详情页数据静默变陈

- 位置：`apps/web/src/features/projects/queries.ts:66`
- 现状：`void qc.invalidateQueries({ queryKey: queryKeys.project(0) })` 失效的是
  `['project', 0]`；真实详情 key 是 `['project', id]`（id ≥ 1），TanStack 前缀匹配
  第二个元素必须恰好是 `0`，**任何写操作都失效不掉详情缓存**。
- 后果：改完资料页面显示旧名称/分类/记录；检查跑完后「推荐」格显示的是**上上次**
  的结论。违反「推荐显示读上次检查的落库结论」的约定。
- 修法：改成 `['project']` 前缀失效全部详情，或在各写操作里按 id 精确失效。
  **必须与 H2 一起修。**

### H2. ProjectFormDialog 填表 effect 依赖 `editing` 对象，表单会被服务端旧值覆盖

- 位置：`apps/web/src/features/projects/ProjectFormDialog.tsx:58-75`
- 现状：effect 依赖 `[formOpen, editingId, editing]`，`editing` 来自 `useProject`，
  任何 refetch 换新引用都会重灌表单。
- 后果：用户敲了一半的表单被服务端旧值整体覆盖。目前被 H1 意外掩盖；
  **H1 修好后此雷立刻发作**。
- 修法：依赖收窄成 `[formOpen, editingId]`，用 ref 或「只灌一次」标记读最新 `editing`。

### H3. 无鉴权写接口有 CSRF 面，`DELETE /api/commands` 给了反取证通道

- 位置：`apps/server/src/app.ts:33`、`apps/server/src/routes/diagnostics.ts:31,42`、
  `apps/server/src/routes/updates.ts:46`
- 现状：Fastify 无 Host/Origin 校验；空 body 的 POST（`ids` 可缺省）不触发 preflight，
  属于「简单请求」，恶意网页可直接对本机 127.0.0.1:5174 发起：
  - `POST /api/updates/check`（空 body）→ 全部非 personal 仓库联网 fetch；
  - `POST /api/auto-fetch`（空 body）→ 一轮联网 fetch；
  - `DELETE /api/commands` → **清空命令日志**——不变量 11（自动做的事必须留痕）的反取证通道。
- 后果：用户浏览器打开任意恶意页面即可触发批量联网、抹掉留痕。DNS rebinding 下 GET 也可被读。
- 修法：校验 `Origin`/`Host` 头（只放行配置的 origin），或写接口要求自定义头
  （如 `X-Git-Nest: 1`）迫使 preflight。改动集中在 app.ts 一处 hook。

### H4. `upstreamGone` 误报 gone，把用户引向删分支

- 位置：`packages/core/src/git/inspect/via-lib.ts:109-124` + `inspect/index.ts:127,155`
  + `via-cli.ts:84`
- 现状：上游是**本地分支**（`git branch -u main` 会写 `branch.x.remote=.`）时，
  库去解析 `refs/remotes/./main` 必然失败 → `upstreamGone = true, upstream = null`；
  随后 `via-cli.ts:84` 看到 `upstream === null` 短路返回，真 git 没机会用 `@{u}`
  （它能正确解析 `remote="."`）纠正。自定义 fetch refspec 同理。
- 后果：报 `gone`「上游分支已被远程删掉」，建议动作是「重新 push -u 或删掉本地分支」
  ——**破坏性建议**，假警报引向真破坏。
- 修法：`remote === '.'`（上游是本地分支）时不走 `refs/remotes/` 拼接，
  交给 CLI 的 `@{u}` 判定；或解析失败时不直接判 gone，降级为「交由 rev-list 反证」。

### H5. pull 写入口没有基线闸，rewritten 场景会静默快进

- 位置：`packages/core/src/git/pull.ts:31-79`
- 现状：唯一写入口不接收 `lastUpstreamSha`、不查基线。脏工作区/detached/分叉三道闸都在，
  「作者改写历史」闸没有。作者 force push 且本地 HEAD 仍是新历史祖先时，
  `pull --ff-only` 会**静默快进**（recommend.ts:28-36 文件头自己点名的场景）。
- 后果：「别更新到被作者重置的仓库」这条最要紧的安全承诺目前只靠用户看推荐自觉。
- 修法：`pullRepo` 接收基线 SHA 参数并在 `rewritten` 时拒绝（或要求显式确认参数）；
  server 的 `runApply` 已有 `update_checks.detail` 判决（不变量 4），把它作为硬条件传下去。
  注意保持「读基线必须在 fetch 之前」（不变量 10）。

### H6. taskStream 定时器泄漏，旧任务复活抢占新连接

- 位置：`apps/web/src/features/updates/taskStream.ts:95-99, 223-229`
- 现状：`close()`/卸载只关 EventSource，不清 `retryTimer`/`silenceTimer`
  （它们活在 `openStream` 闭包里，只有 `giveUp`/`closed` 事件会清）。
- 触发路径：流断 → `onerror` 排了重连定时器 → 用户点 × 或「重新检查」（`reset()` 不清
  定时器）→ 定时器到点为**旧任务**新建 EventSource 并覆盖 `sourceRef.current`，
  把新任务连接顶掉；面板已卸载则是泄漏的连接 + 对已卸载组件 setState。
- 修法：`reset()` 与卸载 cleanup 里 `clearTimers()`；定时器句柄移到 ref 里统一管理。

## 中危

### M1. git stderr 全文进 `error.raw` 并落库，可能含 URL 内嵌凭证

- 位置：`packages/core/src/git/errors.ts:18,75`
- 现状：`classifyError` 把 stderr 全文留在 `error.raw`，'unknown' 类的 `message`
  直接取 stderr 首行。认证失败时 stderr 形如
  `fatal: unable to access 'https://user:token@host/repo.git/': ...`。
- 后果：凭证明文落 `update_checks.detail`（SQLite）并经 API 上前端。命令日志本身干净
  （只记 args 不记 URL），漏的是 stderr 通道。
- 修法：`classifyError` 入口对文本做 `https://user:pass@` → `https://***@` 脱敏
  （正则在 raw 与 message 两条路径上都生效）。

### M2. 「目录被删」误归因为「路径太长」，指引用户修错方向

- 位置：`packages/core/src/git/errors.ts:44-48`，触发面 `log.ts:122-126`
- 现状：git 进不去不存在的目录时报 `cannot change to '<dir>': No such file or directory`，
  path_too_long 正则含 `cannot change to` 且检测顺序在 not_a_repo 之前。
- 后果：仓库被移动/删除后点「检查更新」，用户看到「路径超过 Windows 长度上限…移到浅一点的目录」。
- 修法：path_too_long 正则排除 `No such file or directory`，或调换检测顺序并加一条
  「目录不存在」的归类。

### M3. 设置页数字输入框逐击键发 PATCH，可丢输入、可存非法值

- 位置：`apps/web/src/pages/SettingsPage.tsx:80-117`、`features/settings/queries.ts:26`
- 现状：a) 每击键一次 PATCH 无防抖；b) `onSuccess` 用各自响应 `setQueryData`，
  并发响应乱序时正在输入的值被旧响应回滚；c) 清空输入框 `Number('')` 为 `0`，
  立即作为 `gitTimeoutMs: 0` 提交（min=1000 形同虚设），`1e5` 之类也绕过 min/max。
- 修法：本地 state + 失焦/防抖提交；提交前 clamp/校验；`onSuccess` 不回写正在编辑的字段。

### M4. Dialog 焦点 effect 依赖 `onClose`，SSE 每次事件都抢焦点

- 位置：`apps/web/src/components/ui.tsx:87-94`
- 现状：focus effect 依赖数组含 `onClose`；调用方全传内联箭头
  （`UpdatePanel.tsx:106-109`、`ProjectsPage.tsx:361`）。UpdatePanel 每次 SSE 事件重渲染
  → 新 `onClose` 引用 → effect 重跑 → 焦点被拽回面板第一个可聚焦元素。
- 后果：用户勾选 checkbox 时焦点持续被夺走，键盘操作（空格勾选）失灵。
- 修法：focus 逻辑改为只在 open 翻转时跑一次（依赖 `[open]`），`onClose` 用 ref 读。

### M5. ScanSection 用 `isIdle` 当确认门，导入过一批后闸口永久失效

- 位置：`apps/web/src/features/settings/ScanSection.tsx:111-112`
- 现状：`needsConfirm = picked.size > threshold && importRepos.isIdle`，
  `isIdle` 只在 mutation 从未触发过时为 true。
- 后果：导入过一批（无论成败）后，再勾 30 个仓库**跳过确认**直接导入。
- 修法：换本地 `confirming` state（参照 `UpdatePanel.tsx:91-99` 的正确写法）。

### M6. 删除失败也关弹窗 / 删标签失败静默

- `apps/web/src/features/projects/ProjectsPage.tsx:371`：`onError: onClose` —— 删除失败
  弹窗照关、无提示，用户以为删掉了。修法：失败时 setBanner 且不关门
  （参照 `ScanSection.tsx:310-311`）。
- `apps/web/src/features/settings/TagSection.tsx:65`：`remove.mutate(t.id)` 裸调用无 `onError`。
- `apps/web/src/features/projects/ProjectFormDialog.tsx:108-110,123`：项目本体保存成功后
  `setTags.mutate` 无 `onError` 且紧跟 `closeForm()`——标签没存上弹窗已关。

### M7. status 查询三处旧问题未修

- 位置：`apps/web/src/pages/ProjectDetailPage.tsx:24-27` +
  `apps/web/src/features/status/queries.ts:11-12,38-41`
- a) `fresh: freshNonce > 0`：点过一次「重读本地状态」后 `fresh` 永久为 true，
  之后所有自动 refetch 都绕开服务端 3s 缓存——手动动作污染后续自动读取；
- b) `nonce` 只增不减且拼进 query key：每点一次多一条永不清理的缓存条目（无界增长）；
- c) `statusKeys.batch` 用未排序的 `ids.join(',')`：`[1,2]` 与 `[2,1]` 是两条缓存。
- 修法：`?fresh=true` 只作用于那一次 fetch（mutation 式，不进 query key）；
  batch key 排序去重后再 join。

### M8. getLog 把一切读取失败压成 []，坏仓库显示「还没有提交」

- 位置：`packages/core/src/git/log.ts:97-100`
- 现状：`if (!result.ok) return []`，注释声称只对应空仓库/非仓库，实际超时、index.lock、
  仓库损坏全走这条路。
- 修法：用 `rev-parse --verify HEAD` 区分空仓库；其余失败返回可判别的错误字段，
  前端提交图区域按错误显示。

### M9. parseGitLog 仍会被提交信息里的真实 `\x1e`/`\x1f` 裂行

- 位置：`packages/core/src/git/log.ts:8-29,50-66`
- 现状：git 提交信息只禁 NUL，0x1E/0x1F 是合法字节。subject 含 `\x1e` 时
  `split(RECORD)` 把一条提交切成两段，第 66 行只有 `if (!hash) continue`，
  **没有 40-hex 形态校验**，产生 hash 为文本残片的假提交条目。
- 修法：加一行 `/^[0-9a-f]{40}$/i.test(hash)` 守卫；文件头「任何字符都不会串行」
  的注释改掉。

### M10. 最后提交读不出来 → 状态报「仓库还没有提交」而不是 error

- 位置：`packages/core/src/git/inspect/index.ts:204-206`
- 现状：`hasCommits: facts.hasCommits && lastCommit !== null`，`git log -1` 超时/仓库损坏时
  落到 `deriveStatus` → `no_commits`。
- 后果：详情页/列表页显示「仓库还没有提交」——和假绿同性质的假话，只是换了个方向。
- 修法：`lastCommit === null` 但 `facts.hasCommits === true` 时报 `error` 而非 `no_commits`。

### M11. `GIT_NEST_HOST=0.0.0.0` 时全部写接口对局域网无鉴权开放

- 位置：`apps/server/src/config.ts:10`、README.md 环境变量表
- 现状：无鉴权设计，安全完全依赖默认 `127.0.0.1`；README 列了 `GIT_NEST_HOST` 可调
  但没警告后果（`/api/scan` 还能枚举本机目录）。
- 修法：README 该行加警告「改成 0.0.0.0 = 局域网任何人可改清单、触发 pull、扫目录」；
  更稳的是绑定非回环地址时启动打警告日志。

## 本轮确认没问题的（避免重复排查）

- 密钥/凭证无硬编码；`data/`、`*.db*`、`.env` 均在 .gitignore；`git ls-files` 确认 db 未被跟踪。
- 命令日志不含 URL/凭证；execFile + argv 无 shell 注入面；凭证三保险
  （`credential.helper=` / `GIT_TERMINAL_PROMPT=0` / `GIT_ASKPASS=echo`）到位。
- `GIT_NEST_GIT_TIMEOUT` 幽灵变量已清，有 docs-api-drift 对账测试防回归。
- 依赖版本均为当前线：vite 7.3.6（已修 CVE-2026-39364）、react 19.3.0、fastify 5.12.5、
  better-sqlite3 12.11.1、zod 4.6.5、msw 3.0.0、vitest 3.2.7、isomorphic-git 1.42.4。
  无幽灵依赖（import 全部有声明）。
- tsconfig：`strict` + `noUncheckedIndexedAccess` + `noUnusedLocals/Parameters` 全开。
- 旧审计复核：scheduler 多实例（server 已收拢单实例）、maxBuffer 误报超时、
  limited FIFO、ErrorBoundary（内容区）、整店订阅、`<dd>` 嵌套——均已确认修好。
- 核心安全不变量未被直接违反：无 `reset --hard`/`clean`/`push`；isomorphic-git 只在
  via-lib.ts；基线读取在 fetch 之前；「推荐」显示读落库 verdict、没查过不给绿色；
  不变量 13（一个编辑器）完好。

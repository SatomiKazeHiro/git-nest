## 2. 关键约束

### 2.1 分页与状态筛选是两件独立的事

第一轮**没有分页，但有状态筛选**。原因是：侧栏那五个数字如果不能点，就是我们刚刚清掉的那种死控件
（「未分类」当初就是个点不动的死项）。

分页下一轮单独做，它只加 `page` / `perPage` 与一个计数查询，不改分类逻辑。

### 2.2 计数在这一轮是诚实的

侧栏的计数来自**不带任何筛选的全量查询**（现状已经是这样）。因为没有分页，它数的就是
全部——界面上写 128 就是真的有 128。

下一轮加分页后，这条会失效，那时计数必须走独立查询，不能跟着分页的列表请求走。

### 2.3 `attention` 一次性落在服务端

分类（可更新 / 已同步 / …）**不是 `projects` 表的一列**，它躺在
`update_checks.detail` 这个 JSON 里的 `verdict`，而「哪次检查算数」还有一层规则
（`MAX(id) WHERE status IN (REMOTE_CHECK_STATUSES)`，`repos/projects.ts:212`）。

所以**列表显示、状态筛选、侧栏计数三处必须共用同一份判定**。判定放在服务端、
作为字段返回，前端只渲染不重算——三者不可能漂移，不是靠自觉。

**这一轮就做**。否则会出现「先在 TS 写一遍、下一轮再翻译成 SQL」的返工。

### 2.4 分类与新鲜度是两层

- **分类**（可更新 / 已同步 / …）**时间无关**，可筛选。
- **措辞与色调**（「已是最新」→「上次看是最新」，不变量 5）**时间相关**，不可筛选。

这条边界让筛选不会因为你看久了而漂。

## 3. 数据层

### 3.1 `attention`

服务端算，随列表返回。

```
unchecked ← 没有合格检查（latestCheck 为 null）
blocked   ← verdict ∈ { rewritten, unrelated }      → 不推荐
decide    ← verdict = diverged                     → 需要确认
ready     ← verdict = safe 且 behind > 0           → 可更新
synced    ← verdict = safe 且 behind = 0           → 已同步
```

判定写成**一段 SQL 表达式**（复用 `latestChecksByProject` 已有的
`MAX(id) WHERE status IN (…) GROUP BY project_id` 子查询 + `json_extract(detail,'$.verdict')`），
列表、筛选、计数、详情栏四处共用。TS 侧不再有分类函数。

### 3.2 接口

```
GET /api/projects?category=&tag=&q=&own=&attention=&sort=&page=&perPage=
→ { projects: ProjectListItem[], total: number }
```

- `attention`：可重复（`&attention=ready&attention=blocked`）或逗号分隔
- `sort`：`name`（默认）/ `checked` / `behind`
- `page` / `perPage`：**这一轮先不接受**，下一轮接。响应里 `total` 先带上。

`ProjectListItem` 新增 `attention: 'unchecked'|'blocked'|'decide'|'ready'|'synced'`。

### 3.3 排序

| 选项 | SQL |
|---|---|
| 按名称 | `p.name COLLATE NOCASE`（默认另加：无分类排最后 → 分类 → sort_order → 名称） |
| 按上次检查 | 最新一次合格检查的 `checked_at DESC`，没查过的排最后 |
| 按落后数 | 最新一次合格检查的 `behind_count DESC`，没查过的排最后 |

后两个要 join `update_checks`，与 `attention` 复用同一个子查询。

### 3.4 「同步状态」不需要新数据

`synced` / `ahead` / `behind` / `upstreamGone` 前端已有（`RepoStatus`，lean 档也读）。
判定：

```
上游已关闭 ← upstreamGone
已分叉     ← ahead > 0 且 behind > 0
远程领先   ← behind > 0 且 ahead = 0
本地领先   ← ahead > 0 且 behind = 0
未知       ← 没有合格检查
```

## 4. 界面

### 4.1 侧栏四段

| 段 | 项 | 交互 |
|---|---|---|
| 仓库状态 | 全部仓库 / 可更新 / 已同步 / 不推荐 / 待检查 | 点两下取消；「全部仓库」**只**清掉状态筛选 |
| 我自己的 | 我自己的 | 与其它维度**叠加**（现状如此） |
| 分类 | 只列数据里有的，含**未分类** | 与标签**叠加**（现状如此） |
| 标签 | 只列数据里有的 | 同上 |

**四个维度之间一律叠加，各自独立开关。** 概念图把它们串成「全部状态 / 全部分组」
两个下拉，像是同层的单选——那是概念图的画法，不是我们要的行为：
现在的 `setCategory` 与 `setTag` 互不影响（`store/ui.ts`），这轮也没有理由改。
「全部仓库」只清状态那一个维度，不碰其它三段。

「全部仓库」只在这一段有——它是唯一不是子集的桶，带总数（别处没有），
并给「当前没筛选」一个可见状态。

### 4.2 列表六列

| 列 | 内容 | 宽 |
|---|---|---|
| ☐ 仓库 | 图标 + 名称（14px/600）+ 路径（12px 等宽，第二行） | flex |
| 当前分支 | `main`（12px 等宽） | 7rem |
| 状态 | 药丸 | 6rem |
| 同步状态 | 中性灰药丸 | 7rem |
| 差异 | `↓2 ↑0`（等宽，两个方向都给） | 6rem |
| 上次检查 | 相对时间 | 6rem |
| — | 编辑 / 移出（悬停显形） | 3.5rem |

行高约 44px（两行）。**去掉标签列**——按概念图；代价是列表里看不到某项目挂了哪些标签。

容器查询的收列断点按**清单栏宽度**重算（新列宽下重新量一次）。

### 4.3 列表头

```
[全部状态 ▾]  [全部分组 ▾]  [按名称排序 ▾]        ☐ 全选        1 / 128
```

前两个下拉与左栏**共用同一份筛选状态**（`store/ui.ts` 的 `filters`）。
这是有意的：决定 8 说两边都留着供对比，所以底下必须是一份。
摘掉任何一边都只是摘掉一个视图。

「全选」选**当前筛选出的全部**（这一轮没有分页，所以等于全选）。

### 4.4 状态栏

左：`已选 N 个` + 取消。右：`上次检查 X 分钟前`。

## 5. 视觉系统

`index.css` 的 `@theme` 全换。

```
/* 表面 —— 层次靠明度差，不靠颜色造气氛 */
--bg:        #ffffff     内容区、卡片
--rail:      #f7f7f8     侧栏 / 标题栏 / 工具条
--sunken:    #f2f2f4     输入框

/* 线 */
--line:      #e5e5e8
--line-soft: #f0f0f2

/* 墨 */
--ink:       #0d0d0f     近黑，不用纯黑
--ink-2:     #5c5c66
--ink-3:     #6b6b76     见 5.3

/* 交互：蓝 */
--accent:      #2563eb    实心按钮、图标、选中边框
--accent-ink:  #1d4ed8    蓝字（选中项、链接）
--accent-wash: #eff4ff    选中行 / 选中项底

/* 状态：只有「可更新」是绿的 */
--ok:    #116b32   --ok-bg:    #dcf5e4
--amber: #8a6100   --amber-bg: #fdf3d3
--bad:   #c62a2f   --bad-bg:   #fdeceb
--flat:  #5c5c66   --flat-bg:  #f2f2f4   已同步 / 同步状态
```

### 5.1 蓝与四色共存

> **蓝色 = 你能点的 / 当前选中的。四色 = git 事实。蓝色不出现在两个状态列里。**

两列状态**故意做出强弱差**：

- **状态**列：彩色药丸
- **同步状态**列：**全是中性灰**，刻意比状态列低调

所以三列并排（状态 / 同步状态 / 差异）的读法是：
彩色 = 该动 · 中性 = 上下文 · 数字 = 差多少。

**只有「可更新」是绿的**——绿 = 「去」。

### 5.2 圆角与阴影

```
卡片 10px   输入框 8px   按钮 8px   药丸 999px
选中卡    边框加深 + 极淡阴影 0 2px 6px rgba(13,13,15,.08)
侧栏选中项 白卡浮在灰底上（不是涂一层蓝）
```

阴影只用两级（正常 / 选中）。桌面软件靠明度和线，阴影一多就变网页。

### 5.3 对比度是硬约束

每一对前景/背景都要 ≥ 4.5:1（11.5px 的元信息**不算大字号**，按正文算）。

`--ink-3` 先写了 `#93939d`，算下来只有 3.0:1，不合格；改成 `#6b6b76` 才到约 5:1。
写进注释是因为「灰一点更干净」是本能，而每一档灰都得单独验。

实现时在浏览器里逐对量一遍，不靠估算。

### 6.1 会被这次改动打破的现有用例

### 6.2 新增

- `attention` 五档的判定：每档一条（后端）
- 「无合格检查」与「检查失败」都归 `unchecked`——不变量 9 的那条规则
- 状态筛选与列表显示**用同一份判定**：筛「可更新」出来的每一行，状态列都必须是「可更新」
- 侧栏计数 = 全量，不是筛选后的
- 每一对颜色 token 的对比度 ≥ 4.5:1（浏览器实测，不靠估算）

## 2. 真实 bug（已复现或已由代码结构定死）

### 2.1 【Critical】核心不变量 3 被打破：同一仓库的操作可以并发

- 位置：`apps/server/src/routes/updates.ts:159`、`:191`（对照 `apps/server/src/lib/git.ts:25,52,72`、
  `packages/core/src/git/scheduler.ts:76`）

```ts
// routes/updates.ts:153-159
// 不在这里套 scheduler.map：analyzeUpdates 内部已经按仓库排队并限流了，
// 再包一层会对同一个 path 自锁。
await Promise.all(
  targets.map(async (target) => {
    const report = await analyzeUpdates(target.path, { timeoutMs })   // ← 没传 scheduler
// routes/updates.ts:191
const result = await pullRepo(target.path, { timeoutMs })             // ← 没传 scheduler
```

- 根因：`Scheduler` 的 per-repo `chains` Map 是**实例私有**的。状态查询走
  `lib/git.ts:25` 的 server 实例，批量 check/apply 没传 `options.scheduler` 于是落到
  core 的 `defaultScheduler`（`scheduler.ts:76`）。**两把锁 = 没有锁。**
- 实测复现（把 `Scheduler` 逐字复制到临时脚本，跑两个实例对同一 key 调度）：

```
A 同一实例  : A1:start,A1:end,A2:start,A2:end      ← 串行，符合不变量
B 两个实例  : B1(server):start,B2(core):start,B1(server):end,B2(core):end  ← 交错
```

- 用户可见后果：点「检查更新」/「更新选中的」的同时浏览清单页或详情页，
  同一仓库上 `pull --ff-only`（写工作区）与 `rev-list`/`log`（读 refs）并发，
  正是 `scheduler.ts:1-7` 注释和 `docs/STATUS.md:81` 要防的 `index.lock` / refs 竞争。
- 触发条件：**不需要巧合**——批量任务跑着的时候翻页面就够了。
- 建议修法：`runCheck`/`runApply` 传入 server 的 `scheduler`（`lib/git.ts` 里
  `analyze()`/`pull()` 已经是这个写法，直接复用即可）；更彻底的做法是让「忘记传 scheduler」
  不可能静默降级——例如 core 的入口强制要求 scheduler，或加重入/身份护栏（见 5.2）。

### 2.2 【Important】`analyzeUpdates`：探测失败被当成 `up_to_date`

- 位置：`packages/core/src/git/log.ts:112-133`

```ts
const [ahead, behind] = counts.ok
  ? counts.stdout.trim().split(/\s+/).map((n) => Number(n))
  : [null, null]
...
status: ahead && behind ? 'diverged' : behind ? 'behind' : ahead ? 'ahead' : 'up_to_date',
```

- `counts.ok === false`（超时 / 仓库损坏 / ref 冲突）⇒ `null` ⇒ 三元链一路落到
  `'up_to_date'`。失败被解读成「远程没有任何新东西」，且 `error` 字段保持 `null`，
  失败原因（`counts.result`）被直接丢弃。
- 叠加后果：`routes/updates.ts:172-179` 用 `COUNTED.has(r.status)` 统计桶，
  `up_to_date` 属于「数得上」的状态 ⇒ 失败被计成绿颜色的「N 个已是最新」。
- 建议修法：`counts.ok` 为假时不要落进状态机，返回 `status: 'error'` +
  `toGitError(counts.result, ...)`；并把三元链改成显式 `> 0` 比较，与 `deriveStatus` 一致。

### 2.3 【Important】【已修】`upstreamGone` 在当前 git 上恒为 false（死字段）

> 修复：`60052dd` 之后由 `for-each-ref --format='%(upstream:short)%00%(upstream:track)'`
> 判定（git 的权威结论，上游被删时报 `[gone]`）；并把「上游被远程删掉」提升为
> **独立状态 `gone`**（设计文档 §5 本来就要求覆盖它），不再折叠成 `no_upstream`
> —— 两者的下一步动作完全不同。同时把 `status.test.ts` 那条假绿断言
> （`upstream === null || upstreamGone`）收紧成确定值。
> 回归测试：`packages/core/test/git/upstream-gone.test.ts`（3 例，含「不能误判
> 从来没配过上游」与「上游健在」两个反例）。

- 位置：`packages/core/src/git/status.ts:85-105`

```ts
const upstreamRef = await probe(['rev-parse', '--abbrev-ref', '--symbolic-full-name', '@{u}'], cwd)
let upstream = upstreamRef.ok ? upstreamRef.stdout.trim() : null
...
if (upstream && hasCommits) {            // ← upstream 为 null 时整段被跳过
  const counts = await probe(['rev-list', ...])
  ...
  } else {
    upstreamGone = /no such|unknown revision|bad revision|gone/i.test(counts.result.stderr)
```

- 审计中用真实 git（2.54.0.windows.1）构造「上游配好但 remote-tracking ref 被 prune」：
  `git rev-parse ... '@{u}'` → **exit 128**（`fatal: ambiguous argument '@{u}'`）。
  即 `upstream` 先变 null，`if (upstream && ...)` 整段不执行 ⇒ **`upstreamGone` 永远是 false**，
  第 102 行的正则一行都不会跑。
- 叠加：`RepoStatus.upstreamGone`（`types.ts:57`）在 `apps/web` 全文**零引用**，
  用户看不到「远程分支已删」，只会看到 `no_upstream`，于是被告知去 `push -u`（方向错）。
- 建议修法：用 git 自己的权威判据 `git for-each-ref --format='%(upstream:short)%00%(upstream:track)' refs/heads/<branch>`
  （实测在同样状态下输出 `[gone]`），一次问出上游与是否 gone；`ahead/behind` 仍走 `rev-list`。

### 2.4 【Important】「检查失败」被当成「刚查过」，污染新鲜度 → 假绿「已是最新」

- 位置：`apps/server/src/repos/updates.ts:5-22` + `apps/web/src/features/status/StatusCell.tsx:25-30`
  + `apps/web/src/features/projects/ProjectsPage.tsx:284`

```ts
// repos/updates.ts — 无条件写时间戳，不管这次检查成不成功
INSERT INTO update_checks (project_id, checked_at, status, ...)
  .run(projectId, new Date().toISOString(), report.status, ...)
// StatusCell.tsx
if (!checkedAt) return 'never'
return now - t > STALE_AFTER_MS ? 'stale' : 'fresh'
```

- 链路：`fetchedAt`（= `latestCheck.checkedAt`）语义是「最近一次**点了**检查」，
  不是「最近一次**成功问过**远程」。fetch 失败（断网 / 私有仓库认证 / 超时）时
  `recordUpdateCheck` 照样写 `checked_at = now`，而本地 refs 完全没更新 ⇒
  status 仍是 `up_to_date` + 时间戳很新 ⇒ `toneFor` 给绿字「已是最新」。
- 这恰好击中设计文档第 13 节第 10 条想避免的「没有依据的肯定」，也是核心不变量 5。
- 建议修法：新鲜度只承认成功的检查——`latestChecksByProject` 里过滤
  `status !== 'error'`（或 `update_checks` 增加 `ok` 列），前端 `latestCheck.status === 'error'`
  时按 `never` 处理。
- 备注：切换状态的前提是 status 查询（`?fresh=false`、3s 缓存）先返回旧值。
  该路径成立；若用户点「重新读取」（`?fresh=true`）则会绕过缓存重查。

### 2.5 【Critical】SSE 断流后 `busy` 永真，面板永久卡死

- 位置：`apps/web/src/features/updates/taskStream.ts:96`、`110-113`

```ts
source.onerror = () => setConnected(false)        // ← 只改连接标志
...
} else if (event.type === 'closed') {
  setConnected(false); setBusy(false); close()    // ← 复位 busy 的唯一地方
```

- `closed` 只在服务端收尾时发（`routes/updates.ts:241`）；服务端进程被杀 / 网络断掉时
  永远等不到 ⇒ `UpdatePanel.tsx:82` 的按钮 `disabled={busy}` 永久禁用，
  第 78 行永久显示「N/M · 连接中」。唯一出路是点 ×（走 `reset()`）。
- 同源问题：`closed` 事件里调的 `close()` 关的是 `sourceRef.current`，而事件来自**旧** source；
  若此时已有新连接，会把新连接关掉（`taskStream.ts:64-68` + `110-115`）。
- 建议修法：`onerror` 里 `setError(...)` + 有限重连 + 看门狗（3×心跳无事件则复位 busy 并标 failed）；
  事件回调里先判 `if (sourceRef.current !== source) return`。

### 2.6 【Minor】`Scheduler.limited` 的 FIFO 不成立（无许可泄漏）

- 位置：`packages/core/src/git/scheduler.ts:37-46`
- `start()` 里 `this.active += 1` 是同步的 ⇒「谁被 `shift()` 出来」等价于「谁拿到许可」，
  本身不会超发或泄漏（已按 `setLimit` 放大/缩小、任务同步抛错、任务被拒三条路径推演）。
  但抢许可的时机取决于微任务顺序：新到的任务可能赶在排队任务之前命中
  `this.active < this.limit` 而先跑。本地工具下影响有限。
- 建议修法：把许可获取/归还收敛成单一的 `acquire()`/`release()`，`setLimit` 复用同一个 drain。
- 注：`docs/STATUS.md:141` 说的「偶发失败」，专项实验复刻 `Scheduler` 跑了 300 次
  **零失败**，微任务顺序恰好保护了该用例；结论是「目前不 flaky，但结论依赖时序」。

### 2.7 【Minor】`parseGitLog` 的「任何字符都不会串行」不成立

- 位置：`packages/core/src/git/log.ts:5-22`
- git 不转义 `%s` 里的控制字符。用 `git commit -m $'aa\x1ebb\x1fcc'` 实测输出含真实 `\x1e`，
  按 `\x1e` 切分会把一条提交裂成两条垃圾记录。`\x1f` 反而安全。
- 罕见（粘贴带 RS 控制字符的文本），但注释声称的免疫力是假的。
- 建议修法：改用 git 保证的行边界，或给每条记录加只在开头出现的哨兵前缀。

### 2.15 【Critical】`PATCH /api/projects/:id` 会静默清空未提交的字段（已实测复现）

- 位置：根因 `packages/core/src/schemas.ts:24-26`；后果 `apps/server/src/routes/index.ts:71-85`
  + `apps/server/src/repos/projects.ts:142-147`

```ts
// schemas.ts:24-26 —— .transform() 挂在 .nullish() 外层
remoteUrl: trimmed.max(500).nullish().transform((v) => v || null),
sourceUrl: trimmed.max(500).nullish().transform((v) => v || null),
summary: trimmed.max(2000).nullish().transform((v) => v || null),
...
.refine((v) => Object.keys(v).length > 0, { message: '没有要修改的字段' })
// repos/projects.ts:142-144 —— 键在 patch 里就写库
for (const [key, column] of Object.entries(UPDATABLE)) {
  if (key in patch) { sets.push(`${column} = @${key}`); params[key] = patch[key] }
```

- **实测复现**（用仓库真实 zod，逐字复刻 schema）：

```
parse({})                    -> {"remoteUrl":null,"sourceUrl":null,"summary":null}
parse({name:'x'})            -> {"name":"x","remoteUrl":null,"sourceUrl":null,"summary":null}
--- 修法对照：.optional() 提到最外层 ---
fixed parse({name:'x'})      -> {"name":"x"}
fixed parse({})              -> 被 refine 拦下: 没有要修改的字段
```

- 根因：字段最外层是 `ZodTransform` 而不是 `ZodOptional`，zod 会对**未提交的键**照样执行
  transform，`undefined → null` 后键被物化进输出。于是 `Object.keys(v).length > 0` 恒成立
  （永远 ≥3），**那条 refine 是死代码**；repo 层 `'remoteUrl' in patch` 恒为真，三列一律写 NULL。
- 影响：**任何只改一个字段的 PATCH 都会连带清空远程地址/来源链接/摘要**——
  改个名字、改个分类、改个 path 就会丢数据，而且无声无息。
  现有测试已经在踩（`windows.test.ts:211` 只传 path、`scan.test.ts:224` 不传 remoteUrl），
  但断言里没检查这些字段，所以一直是绿的。
- 修法：`.optional()` 放到最外层（已验证 `{}` → 被 refine 拦下、`{summary:null}` → 保留 `null`
  语义）；同时 repo 层加防御 `patch[key] !== undefined`；补一条「只改 name 时其余字段不变」的测试。
- **注意**：不能把 `.optional()` 放在 transform **里面**（`.nullish().optional().transform(...)`），
  那会让该键变成必填、`{}` 直接抛错。必须包在 transform 之后。

### 2.16 【Important】`GET /api/status` 的 `!` 非空断言撞上清缓存，会 500

- 位置：`apps/server/src/lib/git.ts:75`（对照 `lib/settings.ts:83`、`routes/updates.ts:181,217`）

```ts
// lib/git.ts:67-76
const fresh = paths.filter((p) => { /* 缓存未命中的 */ })
if (fresh.length > 0) {
  const results = await getRepoStatuses(fresh, {...})     // ← 这里让出事件循环
  for (const status of results) statusCache.set(status.path, {...})
}
return paths.map((p) => statusCache.get(p)!.value)        // ← 断言
```

- `fresh` 只含「未命中」的路径；**命中缓存的那部分**在 `await` 期间被另一个请求清掉
  （改设置、改/删项目、任一批量任务收尾都会 `clearStatusCache()`）后，最后一行必然拿到
  `undefined`，`!` 让 tsc 沉默而运行时抛 TypeError → 500。
- 而 `/api/status` 正是列表页高频调用，与「任务刚结束」天然并发。
- 修法：改成 `statusCache.get(p)?.value ?? missingStatus(p)`；更根本的是让缓存失效不依赖
  「清空 + 读取」的窗口——给条目带设置指纹或改成代际计数。

### 2.17 【Important】设置页的 `concurrency` 对三条最重的路径完全无效

- 位置：`routes/updates.ts:159`（check）、`:191`（apply）、`routes/scan.ts:48`（scan）
  —— 都没传 `scheduler`，全部落到 core 的 `defaultScheduler`（`scheduler.ts:76`，并发写死 4）。
- `lib/git.ts:25` 那个「可动态调整」的 scheduler 只被 `repoStatus/repoStatuses/repoLog` 用了。
  设置页把并发改成 1 或 16，对检查/更新/扫描一点作用都没有——用户会以为限流生效了。
- 这与 2.1 是**同一个根因的两个面**：2.1 说「同仓库串行失效」，这条说「跨仓库并发上限失效」。
  修法相同：把 `{ scheduler }` 传下去（`lib/git.ts` 的 `analyze()`/`pull()` 已经是对的写法，
  只是全仓库没人调用——见 4.9）。

### 2.18 【Important】任务清扫会删掉**正在运行**的任务

- 位置：`apps/server/src/lib/tasks.ts:38-42`（`sweep()` 只在 `createTask` 里调）、`:130-136`

```ts
const TTL_MS = 30 * 60_000
export function createTask(...) { sweep(); ... }
function sweep(): void {
  for (const [id, task] of tasks) {
    if (now - task.createdAt > TTL_MS) tasks.delete(id)   // 不看 status，也不看 finishedAt
  }
}
```

- 基准取 `createdAt` 而非 `finishedAt` ⇒ **跑得久的活跃任务被判过期**。
  理论上限：`MAX_BATCH=200` ÷ 并发 4 × 超时 120s ≈ 100 分钟，远超 30 分钟 TTL。
- 更要紧的是清扫时机：`sweep()` 只在 `createTask` 里调用，所以它删掉的很可能是**别人正在跑**的任务。
  任务被摘掉后后台仍持有引用继续跑、继续写库，但 `/updates/:taskId` 与 SSE 入口直接 404，
  前端进度彻底丢失，也没有任何取消路径。
- 修法：TTL 判 `(task.finishedAt ?? task.createdAt)`，且只清 `status !== 'running'` 的；
  `sweep()` 挪到 `getTask` 或定时器里也调；给任务表加数量上限。

### 2.19 【Important】Windows 路径大小写不同 → 同一个目录能在清单里存两条

- 位置：`repos/projects.ts:158-163`（`WHERE path = ?`，SQLite TEXT 默认 BINARY 区分大小写）
- NTFS 不区分大小写，`path` 的 UNIQUE 索引同样区分 ⇒ 同一个目录可以入库两次：
  状态被查两次、`DELETE` 只删掉一条、`scan` 又把两条都标成「已在清单里」。
- 反衬：`routes/scan.ts:117` 与 `core/git/scan.ts:139` 做「是不是同一个」判断时都用了小写比较，
  只有 `pathExists` 这张真正决定唯一性的判据没用。
- 修法：`pathExists` 改 `lower(path) = lower(?)`；更稳妥的是加
  `CREATE UNIQUE INDEX ... ON projects(lower(path))`。三条写入路径共用一个比较函数。
- 附带（同一处脆弱点，当前不触发）：`scan.ts:117` 的 key 是纯 `.toLowerCase()`，
  而查表用的是 `repo.dir.toLowerCase()`——两侧都缺 `normalize` 的对称性。
  实测 `'d:\...' .toLowerCase()` ≠ `'d:/...'.toLowerCase()`，即键不一致。
  当前不触发是因为三处写库都经过 `toAbsolutePath → normalizePath`，落库值都是正斜杠；
  但这是靠约定维持的，不是靠类型。

### 2.20 【Important】`/projects/import` 无事务 + git 异常无兜底 + 并发重复添加落成 500

- 位置：`routes/scan.ts:76-101`（循环里逐个 insert，无 `db.transaction`）、
  `routes/index.ts:187`（`await getRemoteUrl(...)` 无 try/catch）、
  `db/migrations.ts:8`（`path TEXT NOT NULL UNIQUE`）、`app.ts:51-58`（SqliteError 无 statusCode → 500）
- ① `runGit` 的 spawn 失败是 **reject**（不是 resolve），`/projects/import` 与 `POST /projects`
  直接 await，git 不可用时统一 500，而不是「读不到 origin 就先留空」的可降级语义；
  ② import 边校验边写，任一次 insert 抛错则整个请求 500 而**前面的行已经落库**，
  响应体也没机会说清哪些成功（同类写法在 `repos/tags.ts:31-41` 是包了事务的）；
  ③ `pathExists()` 与 insert 之间夹着 `await getRemoteUrl`，两个并发 POST（同 path、都不带
  remoteUrl）会双双通过检查，第二个撞 UNIQUE → 500，`conflict()` 的 409 分支形同虚设。
- 修法：import 包 `db.transaction()`；`getRemoteUrl` 调用点降级为 `null`；
  在全局错误处理器里把 `SQLITE_CONSTRAINT_UNIQUE` 映射成 409。

## 4. 解耦与优化机会

### 4.1 分层不一致：notes/tags 的 SQL 漏在路由层

- `routes/index.ts:119-124`（POST notes）、`:135-137`（PATCH notes）、`:145`（DELETE notes）、
  `:161-164`（tag 重名检查）直接写 SQL / 直接调 `db.prepare`，而 `repos/projects.ts`、
  `repos/tags.ts` 已经建立了 repo 层。
- 建议：把 note 的增删改移进 `repos/notes.ts`（或 `repos/projects.ts`），路由只做校验与编排。
  这是当前最便宜、收益最直接的一处解耦。

### 4.2 三份 query-key 前缀硬编码 + 两套状态文案表

- invalidate 列表重复三处：`UpdatePanel.tsx:27-31`、`projects/queries.ts:49-56`、`ScanSection.tsx:42-44`。
- 「状态 → 一句话」有两套：core `status.ts:213 describeStatus`（**全仓库无调用点**）
  与前端 `StatusCell.TEXT`。`↓N/↑N` 的渲染也有两处（`StatusCell.Delta` / `UpdatePanel.ReportCell`）。
- 建议：收敛成 `queryKeys` + `invalidateAll()` 单一出口；文案表只留一套（core 那份要么用起来要么删掉）。

### 4.3 重复的 git 调用：导入时重问一次 remote

- `routes/scan.ts:90` 对每个待导入路径再跑一次 `git remote get-url origin`，
  而 `/scan` 的响应里已经带了 `remoteUrl`（`scan.ts:53-67`）。
  批量导入 200 个仓库 = 200 次多余进程启动（Windows 上每条几百毫秒）。
- 建议：`/projects/import` 接受前端回传的 `remotes` 映射，命中则跳过。

### 4.4 `getRemoteUrl` 是全仓唯一「裸」git 入口

- `status.ts:198-201` 不接 `timeoutMs`/`scheduler`，硬用默认 120s，且不排队。
  设置页改的超时对它无效（手动添加项目 / 扫描导入路径）。

### 4.5 `getLog` 的 `all` 选项语义反直觉

- `log.ts:60`：`options.all === false ? 'HEAD' : '--all'` —— 默认 `--all`，
  只有显式传 `false` 才只看 HEAD，且这个选项在任何文档里都没写。

### 4.6 每仓库 8 条 git 命令【已优化】

- `readStatus` 原来逐个 probe（is-inside / porcelain / HEAD verify / symbolic-ref /
  上游 for-each-ref / rev-list / remote / log）。**已合并**：改用
  `git status --porcelain=v2 --branch`，它的头部一次给出「有没有提交 / 分支 /
  detached / 上游 / 领先落后」，其余行就是脏标记；预检也去掉了（失败时的报错本身
  能区分「不是仓库」与「路径进不去」）。
- **实测**（`runner.ts` 的 git 子进程计数 + `test/git/status-spawns.test.ts`）：
  读状态 **7–8 条 → 3 条**（非仓库目录 1 条）。
  `analyzeUpdates` 顺带去掉预检与单独的 `@{u}`：**10 条 → 8 条**。
  100 个仓库从约 800 次进程启动降到约 300 次。
- 顺带发现一个更准的判据：**「有 `branch.upstream` 行、但没有 `branch.ab` 行」
  = 上游被远程删了**（prune 之后正是这形态），所以 `gone` 也不必再单独跑 for-each-ref。
- 安全网：`test/git/status-equivalence.test.ts`（14 例，断言完整的 RepoStatus
  关键字段而不只是 status 枚举）+ `test/git/status-spawns.test.ts`（9 例，钉住上限，
  以后谁往这些函数里加探针就会红）。

### 4.7 前端（会丢输入/非法 DOM 的已提到 2.13，这里只列解耦与性能）

- `ProjectsPage.tsx:158` / `ProjectFormDialog.tsx:43` 用整店订阅 `useUiStore()` 无 selector，
  勾一个复选框会让 Toolbar 与整棵行树重渲染（功能正确，纯性能）。
- `GitGraph.tsx:7-17`：`useQuery` 写在组件文件里，而 `status/queries.ts`、
  `projects/queries.ts`、`settings/queries.ts` 都是独立 queries 文件 —— 格式不统一。
- `layout.ts:116` 的 `width` 裁剪分支是死代码预算：`useGraphLayout` 从不传 `width`，

## 6. 未确认的疑点

### 6.4 泳道图车道泄漏：已确证，**已通过换回库解决**

专项实验（用 Node 22 原生 TS 直接 import 真实 `layout.ts`，跑了 1223 个用例，
含 7 个真实仓库的 `git log --all -n 120`）确证了两件事：

1. **车道永久泄漏**（确证）。`!continues` 分支只释放「当前这条线」经过的列，
   而「基点不是 root 的 merge」会让第二个父提交预定过的列从此无人释放。
   真实仓库 archify（120 提交、19 个 merge）量到 `laneCount=40`，其中
   `5,7,14,18,24,31,35,37` 这 8 条列没有任何节点或连线引用；
   再被 `width = Math.min(200, …)` 一夹，**75/120 个提交点被画到 SVG 画布外**。
   最小复现：7 个提交的两路菱形堆叠 12 次 → `laneCount=37`（应 ≤3）。
2. **我原先猜的 bug 不成立**（实验否证）。「lane 被释放后又被别的分支占用、
   导致 pending claim 的预期 lane 被抢走」在 1223 个用例（含 3455 次释放路径）
   中 **0 次**出现。真正的病灶是「释放条件太保守」，不是「被抢」。

另外确证的同源渲染问题（属于「线粘连」）：
`edgePath` 把换道折点放在边中点，导致长距离 merge 线的竖段长时间占用源列、
穿过无关提交的圆点（真实仓库 Kun 实测 18 处穿点 + 20 处共列）。

**结论与处置：不再自研，换回设计文档原本指定的 `@tomplum/react-git-log`。**

- 走过一段弯路：先试了三种改法修那个增量集合（引用计数、自顶向下定向、
  兄弟列去重），全部破坏了列顺序规律（线性历史排成 `[0,1,0]`）。
  这属于**设计问题不是补丁问题**：正确做法是按「行区间」分配列，等于重写分配器。
- 而设计文档第 4 节原本就指定了这个库（「可插拔弱依赖，不可用则自研替换」），
  当初自研是走了「替换」那条路。库是维护中的（3.5.1，Apache-2.0，
  peer 要求 react >= 19 —— 本项目正好是 React 19），这类图布局 bug 整类不存在。
- 现在 `features/gitgraph/GitGraph.tsx` 是薄封装（取数 + 字段映射），
  `layout.ts` 与 `layout.test.ts` 已删除，换成 `GitGraph.test.tsx`
  （断言提交标题/作者/分支真的渲染出来）。
- 顺带一处语义调整：`getLog` 默认只取当前检出分支（不再 `--all`），
  因为库按 `branch` 组织图，混入别的分支会让提交归属说不清。

## 7. 审计中确认**不是**问题的事项（避免重复排查）

- **没有 SQL 注入 / 命令注入**：`listProjects` 的 WHERE 片段是常量拼接 + 命名参数，
  `IN (...)` 全是 `?` 占位，`updateProject` 的列名来自 `UPDATABLE` 白名单；
  git 一律 `execFile` + argv 数组、不走 shell。
- **外键与级联删除真的生效**：`db/index.ts:15-16` 在 `migrate()` 之前设了
  `PRAGMA foreign_keys = ON`（不在事务里，所以生效）。实测删项目后
  notes / project_tags / update_checks 孤儿行为 0。
  注意这是**连接级**设置，另开一个不带 pragma 的连接级联会静默失效。
- **`Scheduler` 的许可计数没有泄漏**：按 `setLimit` 放大/缩小、任务同步抛错、任务被拒
  三条路径推演过，`active` 都能归零。
- **`update_checks` 的事件缓冲不是无界的**：每项最多 2 条事件 + started/finished，
  200 项实测 401 条。真正无界的是**任务数量**（`tasks` Map 无上限，见 2.18）。
- **fire-and-forget 的 rejection 有兜底**：`routes/updates.ts:65-67`、`:82-84`
  都是 `void runX(...).catch(...)`，内部每个 item 还有 try/catch。
- **SSE 用 `reply.raw` 而没 `reply.hijack()` 不是 bug**：Fastify 5 的 `reply.sent`
  getter 已包含 `raw.writableEnded`，handler 返回 undefined 不会二次发送。
- **`onUnhandledFrame` 不是笔误**：msw 3.0.0 的正确选项名，类型定义可查，typecheck 通过。
- **`lib/api.ts` 的封装是统一的**：全仓只有 `lib/api.ts:17` 一处裸 `fetch`。

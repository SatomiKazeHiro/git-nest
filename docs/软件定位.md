# 软件定位

> **一句话**：把散在本机各处的 git 仓库收进一张表，让「每个仓库现在跟远程差多少、能不能安全拉」
> 变成**一条可读、可靠、随时更新的数据**；联网只发生在 fetch，动你的工作区只发生在你勾选之后的
> fast-forward。

这份文档回答的是**「这是什么、为什么长这样、什么不做」**。在「它是什么 / 什么算核心业务」这一层，
**以本篇为准**。

---

## 1. 它解决的那一个问题

一个人手上有几十个仓库散在各个目录里。他每隔一段时间只想回答三句话：

1. **有哪些**仓库（现在它们在哪、属于什么分类）；
2. **哪些要我动手**（落后了、或者是作者改写过历史的危险更新）；
3. **动手会发生什么**（能快进吗？会拉进来哪些提交？会不会把我本地的东西搞坏）。

这三个问题的答案**全在本机算得出来**——除了「远程此刻是什么样」，而那个只能靠 fetch 去问。

**明确不解决**：不写代码、不做 merge / rebase / 冲突解决、不托管仓库、不管分支策略。它是一个
「看状态 + 拉快进」的工具，不是一个 Git 客户端。

## 2. 核心业务只有一个动作

```
sync(仓库)   = fetch + 算        →  RepoState（这个仓库此刻的远程状态）
update(仓库) = sync(仓库) + ff-only（只允许 fast-forward）
```

`RepoState` 的内容就是那三个问题的答案：

| 字段 | 回答的问题 |
|---|---|
| `behind` / `ahead` | 差多少 |
| `verdict`（判决） | 能不能安全拉 |
| 最近要拉进来的提交（前几条 + 总数） | 拉进来的是什么 |
| 上游 SHA（这次看到的） | 下次判「作者改写过历史」的基线 |
| `checked_at` | 这份数据是什么时候拿的 |

**这是本篇最该被记住的一条**：系统里只有这一个动作，其余全是它的**触发器**，不是它的替代品。

| 触发器 | 就是 |
|---|---|
| 启动时一轮、之后每 :00/:30 一轮（休眠恢复补跑） | sync 全部仓库 |
| 顶部「刷新」 | sync 全部仓库 |
| 「检查更新」 | sync 选中的仓库 |
| 「更新」 | sync 之后 fast-forward |
| 单仓库「重试」 | sync 那一个仓库 |

四个名字、一个动作。**任何「不 sync 就给状态」的路径都是错的**——那等于凭空造一个结论。

## 3. 一个仓库一条数据（主体表）

| 表 | 装什么 | 在业务里的位置 |
|---|---|---|
| `repo_state` | 每个仓库一行：`behind / ahead / 判决 / 最近提交 / 上游 SHA / checked_at / 错误` | **主体业务** |
| `projects` | 路径、分类、是不是我自己的、我的「记录」 | 元数据（人写的，寿命长） |
| 标签 | 多值，`tags` + `project_tags` | 元数据 |
| `commands` | 每条 git 命令的日志 | 旁路：谁在什么时候起了什么命令 |
| 检查流水 | 每次 sync 追加一行 | 派生数据，随时可删 |

三条判断写在前面，免得以后又长回去：

- **「当前状态」就该存成当前值，不要靠「从历史里挑最新」去得到**。后者会让同一个事实拥有
  第二种读法（相关子查询 + 解析 JSON），于是每加一个字段就要在两处保证一致。
  历史是另一件事：想留就单独留，别拿它当状态表用。
- **元数据与状态的寿命不同，不要混在一行里现算**。改名、加标签是你偶尔改一次的；落后数半小时
  一变。写次数会被短寿命的那一半绑架，读的时候又得把两种时间混在一个时间戳里。
- **标签天生是多值**，无论状态表怎么设计它都要单独一张表——那不是复杂度，是关系模型的下限。

统一的口径是一句话：**一个仓库在主体表里只有一行，那一行就是它此刻的全部结论；其余的表要么是
元数据，要么是旁路，要么是可删的派生物。**

## 4. 远程事实与本地事实，分开

| | 例子 | 存在哪 | 谁改它 |
|---|---|---|---|
| **远程事实** | 落后 / 领先 / 判决 / 要拉的提交 / 上游 SHA | `repo_state` | 只有 sync |
| **本地事实** | 当前分支、工作区脏不脏、游离 HEAD、目录还在不在 | 不入库，现场读 | 你（切分支、改文件、删目录） |

理由：后几种在两次 sync 之间**会自己变**。把它们也写进快照，等于给它们设一个会过期的假值。

一条推论，也是界面上的硬规矩：**每一格都要能说出「我这一格是什么时候、由谁算出来的」**；
同一行里不许混三个不同时刻的数字。（现状里「差异」列读实时 refs、「判决」列读上次 sync，
就是这条规矩的反例，见 §10。）

## 5. 判决是核心产出，必须落库

判决只有这几个词，词表本身是产品的一部分：

| 判决 | 说法 | 下一步 |
|---|---|---|
| `safe`（且落后） | **可更新** | 勾上，快进 |
| `diverged` | **要你决定** | 两边都往前走了，得你自己合 |
| `rewritten` | **别拉** | 作者 force push 过，拉会分叉 |
| `unrelated` | **别拉** | 这不是更新，是换了个仓库 |
| `gone` / `no_upstream` | 上游没了 / 没上游 | 先去修上游 |

三条规矩：

1. **判决由纯函数算**（给定事实 → 结论），与「读事实」分开。读事实要跑 git，下判决不该再跑一遍。
2. **判决必须落库**：它同时是 ① 清单上那句话 ② 「更新」那一步在服务端的闸（前端禁勾只是建议）。
3. **「别拉」的两种不能合成一个词**：作者改写历史 与 作者换了仓库，用户的下一步动作完全不同。

## 6. 三条红线（永远不让）

1. **联网只发生在 fetch**，而 fetch **只动 `refs/remotes/*`**，不碰工作区、不动 HEAD；
2. **动工作区只发生在你勾选之后的 fast-forward**——不产生 merge commit，不解决冲突；
3. **绝不** `merge` / `rebase` / `reset --hard` / `clean` / `push` / 改写历史。

另有一条不算红线但同样要守：**更新完之后必须立刻知道自己变成了什么状态**。
「更新成功但之后半小时显示没有数字」等于让用户在最该确认的时刻失去确认。

## 7. 新鲜度怎么说话

- 远程事实**一律带时间**（`checked_at`）。超过 12 小时就降级成「上次看是最新」，颜色转灰；
- 纯本地事实**永远直说**，不加限定语——它不依赖远程；
- **数据一直新的时候，话就不用打折**。定时同步常态化之后，「上次看是…」很少出现，这是设计目标，
  不是 bug。

## 8. 明确不做（非目标）

- 不做云端、多用户、多人共享、托管或同步服务。**本机单用户、无鉴权**是前提，不是过渡状态。
- 不做浏览器里的多人产品形态（也不为它加鉴权）。
- 不做 merge / rebase / 冲突解决 / 分支策略建议。
- **不做定时自动更新**。定时只同步状态；动工作区永远要你勾选。
- 不做趋势分析、统计报表、通知推送。检查流水是派生物，别为它加字段。
- 不做「第二份真相」：任何缓存只能是同一份真相的短期记忆，不能自己长出结论。

## 9. 怎么用这份文档判一个需求

新需求进来，先问三个问题：

1. 它让「一个仓库一行状态」**更权威**，还是又造出**第二份真相**？
2. 它需要联网吗？需要的话，**是不是 fetch**？
3. 它会不会让「能不能拉」多出**第二个判据**？

三个都过关才做。任何一条过不去，先改设计再写代码。

## 10. 现状与这份定位的差距

这张表就是重构清单。每消掉一行，系统里就少一处「同一个事实的第二种读法」。

| 差距 | 现状 | 目标 |
|---|---|---|
| **状态没有单一归属** | 实时读 refs（清单差异列）+ 从历史挑最新（判决列）+ 任务内存里的报告（弹窗） | 只有 `repo_state` |
| **核心动作写了两遍** | `analyzeUpdates()` 与 `pullRepo()` 各自 fetch、各自判「改写历史」 | 一个 `sync()`；`update` = `sync` + ff-only |
| **更新后没有状态** | 「更新」写一行 `behind/ahead` 为 null 的记录 | 更新完立刻有完整状态 |
| **提交列表不落库** | 只在弹窗那一次任务的内存里 | 进 `repo_state`（前几条 + 总数） |
| **同一行三个时刻** | 「差异」列实时、「判决」列上次 sync | 同一来源、同一时刻 |
| **弹窗重复了清单** | 「检查」在弹窗里，结论又要在清单里看 | 一条数据 + 若干触发器，界面只是它的两种视图 |

---

**维护这条规矩**：以后凡是「要不要在界面/接口/数据库里加第二个地方来回答同一个问题」的讨论，
结论先落到这份文档里，再改代码。
